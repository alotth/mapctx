## Implemented contract

- `mapctx validate` under `plansAuthority = "store"` reads `mapctx.toml` for project identity and a read-only store handle for canonical validation. It does not read `TASKS.md` or local task details. Pending schema/journal maintenance returns an explicit `maintenance-needed` status without repair or migration.
- **Canonical structural validation (restored in attempt 2; warnings completed in attempt 3, review F1/F2/N3).** The canonical validator recomputes the markdown validator's still-applicable guarantees from projections: date formats (`invalid-start-date`, `invalid-due-date`, `invalid-completed-date`, `invalid-updated-date`), `specMode` enum, planning/execution state enums, task type enum, non-empty title, domain membership against the project's declared Work Domains (`invalid-domain`, `domains-without-work-domains`), parent/dependency endpoint existence in BOTH directions (`unknown-dependency-source`), dependency kind vocabulary (`unknown-dependency-kind`), parent/dependency cycles, epic/non-epic ID-prefix warnings, and done-Acceptance completeness. Attempt 3 added the two remaining applicable WARNINGS at their original severity, DB-only, never gating: `external-id-format` (`<provider>:<entity>:<id>` shape) and `empty-work-domains` (no declared Work Domain keys). Markdown-only formatting rules (key order, heading shape, file existence, subIssueProgress) are intentionally absent — the canonical validator is NOT a port of the markdown formatter; it enforces the store's own structural contract. Date ordering (`completed-before-start`, `due-before-start`) compares only when BOTH dates are present and well-formed — a null `dueDate`/`completedOn` next to a `startDate` is valid, never "before" (F1).
- **T-092 semantic reconciliation (planned, localised).** `completion-date-missing` applies to `done` only. `cancelled`/`archived` are terminal WITHOUT completion: null `completedOn` is legitimate, and a legacy date on a terminal task is preserved and format-checked, never invented or stripped. Non-terminal states with `completedOn` remain invalid. This aligns the validator with real `moveTask` behavior (which stamps `completedOn` only for `done`); it is a validator reconciliation, not a lifecycle/FSM change, and mutates no history. Markdown-authority validation keeps its previous board-based rule.
- `mapctx validate --snapshots` opts into local Markdown structure and drift checks. This path does not affect the canonical result. Markdown-authority validation keeps its previous board-based behavior.
- Store migration 10 adds Acceptance revision and criterion projections and a checkpoint source-state field. Acceptance changes use journal events. A criterion carries stable identity, revision, source, state, and approval/evidence facts. A new revision resets every criterion to pending — and (F5) admission now REFUSES a raw `acceptance.revised` whose criteria carry `approvedAt`, `approvedBy`, or `evidence`, before the journal write, so approval state can never be smuggled into a new revision. Approve/unapprove require expected revision and criterion id or index; the library functions `reviseAcceptance`/`approveAcceptanceCriterion`/`unapproveAcceptanceCriterion` now REQUIRE `expectRevision` in types and at runtime — there is no silent latest-revision default (F7). This is a deliberate breaking change for direct library callers; the CLI already required `--expect-revision`. Refusals without it return `revision-conflict` with `expectRevision is required` messaging and write zero events. The `--index` selector is convenience, resolved inside the write transaction against the caller's expected revision.
- `mapctx acceptance import` is dry-run by default; `--commit` is explicit and applies a preflighted batch in one write transaction. It parses the same bytes it hashes. `[x]` becomes `approved` with `import-observed` provenance, `[ ]` stays pending, missing section stays absent, and a present empty/prose-only section is an empty revision. Planning `done` never implies approval. Existing Acceptance revisions are skipped.
- Routine claim/start/update/receipt/move and budget writes no longer regenerate mirrors. `mapctx export` publishes an explicit checkpoint. `mapctx task finish <id>` applies the canonical done gate, then publishes a task-end or epic-end checkpoint. `wave-end` remains an explicit label; there is no wave controller or automatic wave-end trigger.
- Acceptance prose handling is driven by ONE shared tokenizer, `analyzeAcceptanceProse` in `@mapctx/core` (attempt 3, review N1): `parseAcceptanceChecklist`, `stripAcceptanceSection` and `hasUnterminatedFence` are all derived from it, so parse and strip can never diverge. Fence subset (documented, NOT full CommonMark): a fence opens on a line whose first non-whitespace characters are a run of >= 3 backticks or tildes; a backtick fence's info string cannot contain a backtick (so inline spans like ```code``` are prose); a fence closes on the SAME character with a run at least as long and nothing but whitespace after; fence recognition is INDENT-INSENSITIVE because the detail-file description block is indented 6 spaces in raw detail bytes — a deep-indented fence must stay fenced (the "naive <=3 spaces" hazard from review N1). Everything inside a fence is opaque: no section can open/close and no bullet can be a criterion there. The import parser uses the same tokenizer, so fenced examples are never observed approvals.
- **Unterminated-fence refusal (attempt 3, review N1).** When a task's kept prose opens a fence outside a real Acceptance section and never closes it, there is no safe boundary for re-inserting the generated section — rendering would swallow prose or grow the mirror on every export. Export and push therefore REFUSE explicitly (`acceptance-render-refused`) BEFORE any filesystem or remote write: nothing is published, no checkpoint is recorded, the Git prose stays byte-unmodified, and repeated attempts refuse identically with zero growth (stage `build` for checkpoints). The remedy is in the Git prose (close or remove the stray opener). Prose WITHOUT canonical revisioning is never refused and stays byte-compatible. `validate --snapshots` reports the refusal as an honest drift issue instead of crashing, and no pass is promised after a refusal. Strip output is idempotent over a 3000-document mixed corpus checked against an independent reference of the documented subset.
- Store-backed GitHub push renders the issue-body Acceptance from the CANONICAL store revision, stripping whatever Acceptance the mirror carries (F4; N4). A stale `[x]` in the mirror can never replace current pending criteria on GitHub. When the detail mirror is ABSENT (e.g. a worktree without `tasks/`), canonical criteria are still published, preceded by an explicit note that Git-authored prose is unavailable in that checkout — absent prose is reported, never reconstructed or fabricated (N4). With no canonical revisioning, no Acceptance section is published (documented absent). No real GitHub calls were made (fake runner in tests only).
- Checkpoint content, event cursor, and Acceptance revision source are read under one write transaction. Publication uses temporary files and per-file rename. The checkpoint event is appended only after every file publishes. A partial failure leaves accepted canonical mutations intact, reports files already published, and records no checkpoint. Retrying finish after canonical `done` rechecks current Acceptance, skips a duplicate move, and retries publication.
- **Finish precondition under the publication lock (F6).** `finishTask` passes a precondition (planning state `done` + the acceptance revision observed at gate time + acceptance completeness) into `publishCheckpoint`, re-verified inside the SAME `BEGIN IMMEDIATE` transaction BEFORE any filesystem write. A concurrent revise or reopen in the gate-to-publication gap refuses with failure stage `precondition` (CLI reason `checkpoint-precondition`), writes no files and records no checkpoint, and declares that the canonical done mutation (if any) remains accepted plus the observed state. The retry-already-done path rechecks under the same lock. A refused precondition leaves no temp files. Manual export takes no precondition and never pretends every task is done.

## Data and recovery limits

Checkpoint records carry file SHA-256 hashes, source event cursor, reason, and Acceptance revision map. A multi-file publication is not globally atomic: an interrupted run can leave a partial local mirror set, which `mapctx validate --snapshots` detects. A checkpoint contains Markdown mirrors, not complete journals, receipts, evidence, corrections, or attestations. Git-authored task description prose remains outside store recovery.

Migration 10 is additive. Validation does not run migrations, repair, or reindex. The worker did not migrate or adopt the live store; coordinator owns live-copy preservation proof and application after independent review, including T-119 attested nodes.
