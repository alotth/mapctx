  - summary: Support custom status workflows and configurable completion states throughout sync operations.
  - description: |
      ## Product Context
      Teams use different workflow vocabularies, so hardcoding `done` and one default status set limits adoption.

      ## User Story
      As an operator, I want custom allowed statuses and completion states so local boards and GitHub sync can match my real workflow.

      ## Expected Outcome
      Status validation, pull/push/bootstrap/reconcile behavior, and completion-date semantics all respect configured workflow rules.

      ## Acceptance
      - [x] Support dynamic `allowedStatuses` with runtime validation.
      - [x] Support configurable `completionStatuses` without hardcoded `done`.
      - [x] Preserve custom statuses across `status`, `pull`, `push`, `bootstrap`, and `reconcile`.
      - [x] Add regression and custom-workflow tests.
      - [x] Update docs and config examples for default and full-replacement workflows.

      ## Decisions Taken
      - [2026-02-24] Completion-date semantics follow configured completion statuses instead of assuming `done`.

      ## Implementation Notes
      - Added status normalization and validation helpers in `packages/sync-engine/src/statuses.ts`.
      - Extended config and type models to accept dynamic status keys.
      - Added workflow regression coverage in `packages/sync-engine/src/status-workflows.test.ts`.
