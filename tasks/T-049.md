# T-049

  - role: backend
  - impact: high
  - estimatedEffort: 1w

  - blocking: [T-058]

  - summary: Add external SQLite/event store, project identity, Markdown import, and deterministic export.
  - description: |
      ## Product Context
      Agents in separate worktrees need one atomic live state without editing competing Markdown copies.

      ## Expected Outcome
      `mapctx.toml` resolves a shared store; current TASKS data imports safely; snapshots remain reproducible.

      ## Acceptance
      - [x] Use WAL and atomic claims.
      - [x] Import current board without losing IDs or durable intent.
      - [x] Generate deterministic TASKS.md compatibility output.
      - [x] Keep event-derived fields out of authored Markdown.
      - [x] `mapctx.toml` gains `plansAuthority: markdown|store`, defaulting to `markdown`. `mapctx import` is the only writer of this field; it flips it to `store` in the same commit that lands the first generated snapshot. That commit is the cutover — an observable git event, never a date.
      - [x] Drift check recomputes canonical Markdown from current store state and compares it, byte-for-byte after LF-normalization and trailing-whitespace trimming, against the on-disk file. No mtime (does not survive `git checkout`/merge) and no separately stored hash (needs its own invalidation rule that regenerate-and-compare avoids).
      - [x] `mapctx validate` runs the drift check only when `plansAuthority: store`; under `markdown` it is skipped, so pre-cutover repos are unaffected. A mismatch is reported as an `error` (same severity tier as other contract violations), enumerated per task ID, non-zero exit. It is never auto-merged.
      - [x] `mapctx reconcile <task-id>` exists as the exit path for a good-faith manual edit: diffs the drifted block against store state and requires an explicit per-field choice — discard the edit (regenerate from store) or accept it (write it into the store as a new event with `source: manual-reconcile` provenance).
      - [x] A worktree/clone with `plansAuthority: store` but no local `~/.mapctx/projects/<id>/mapctx.db` is detected as "not materialized" (not pre-cutover) and tooling fails closed — refuses to treat Markdown as authoritative, directs the user to `mapctx store init` instead of silently falling back.
      - [x] Round-trip `store → TASKS.md/tasks/*.md → store` is lossless for every field T-048's migration mapping marks `persist` or `derive`, proven by both a property-based test (generated store states → export → reimport → fixed point on the Markdown-representable field set) and golden fixtures pinning real edge cases (multi-line description, unicode, epic with subtasks, empty optional fields).
      - [x] Losslessness explicitly excludes event log entries, `UsageEvent`/`CostEvent`, `Dispatch`/`RunReceipt` detail, and `EstimateSnapshot` history — none of these had a Markdown representation before vNext. Downgrading to `plansAuthority: markdown` does not invent one for them; they remain, undeleted, in the now-non-authoritative store directory.
      - [ ] `mapctx export` (the deterministic generation path required above) runs automatically at end-of-wave and end-of-epic, in addition to being callable on demand — the exit hatch does not depend on a human remembering to trigger it before it's needed. **Partial**: `mapctx export --reason manual|wave-end|epic-end` exists and is fully callable on demand (writes a `checkpoint.exported` event either way). The automatic trigger at wave/epic completion is not wired up — there is no wave-execution or epic-completion-detection code path in this repo yet to call it from (that lives with T-058's dispatch/wave orchestrator). Flagging for T-058 to call `mapctx export --reason wave-end|epic-end` at those boundaries once it exists.
      - [x] The canonical append-only event journal is persisted independently of `mapctx.db` and fsynced before its SQLite event index/projections commit; `mapctx store repair` rebuilds a corrupt SQLite file from that journal after validating per-event hash and contiguous `(nodeId, sequence)` ranges.
      - [x] `mapctx store repair` rebuilds `mapctx.db` by reprojecting from the independent journal when the SQLite file fails an integrity check; a log entry unreadable at a given `(nodeId, sequence)` is reported as a named gap, never silently skipped.
      - [x] Losing the entire `~/.mapctx/projects/<id>/` directory recovers only back to the last git-committed Markdown checkpoint; this starts a new store incarnation (fresh event epoch), and the tool states in `--help` and error/response text that event history strictly older than that checkpoint is permanently gone. **Note**: implemented on `mapctx store init` rather than `mapctx import` — `mapcx.toml` is git-tracked and survives local store loss, so `import --commit` (which refuses when `mapctx.toml` already exists) is the wrong re-entry point; `store init` is also what the "not materialized" error already directs users to, so recovery and first-materialization share one command.
      - [x] `mapctx import` reads exactly one pre-cutover config, `./mapcs.config.json`, carries its GitHub binding into `mapctx.toml`, and deletes it in the same cutover commit. No fallback chain and no merge across files; a repository holding both after cutover fails validation. See ADR 0003 §Configuration succession.
      - [x] Import treats the inherited `projectId`/field IDs as unverified: it records them without contacting GitHub, and `mapctx sync status` reports a named "unverified GitHub binding" state until a successful authenticated read confirms them. Missing `read:project` scope is reported as that scope by name, not as a generic auth failure.
      - [x] Docs state explicitly that MapCtx guarantees checkpoint generation and recovery tooling (`mapctx store repair`, `mapctx store init`); backing up `~/.mapctx/projects/<id>/mapctx.db` beyond checkpoint granularity, and committing the generated checkpoint to git, are the user's responsibility. MapCtx adds no cloud backup or replication service in v1. (`--help` text; see Decisions Taken for the doc-file gap.)

      ## Decisions Taken
      - [2026-08-15] Authority is binary and git-tracked via `mapctx.toml#plansAuthority`; cutover is the commit that flips it, not a wall-clock date. See ADR 0003 §Authority and cutover.
      - [2026-08-15] Drift detection is regenerate-and-compare (canonical Markdown vs. on-disk, hashed after normalization), not mtime and not a persisted hash.
      - [2026-08-15] Drift is `error` severity and reconciled only through explicit `mapctx reconcile`; silent merge is never an option.
      - [2026-08-15] `plansAuthority` is a property of the project (git-tracked), not of the checkout; a missing local store under `plansAuthority: store` is a "not materialized" failure mode, distinct from pre-cutover.
      - [2026-08-15] Lossless round-trip scope is exactly the Markdown-representable field set from T-048's migration mapping; event log, usage, cost, receipts, and estimate history are store-only and out of scope for the exit hatch. See ADR 0003 §Durability and rollback.
      - [2026-08-15] Export checkpoints run automatically at wave/epic boundaries, not only on manual invocation, so the exit hatch stays current without a human trigger.
      - [2026-08-15] Corruption recovery is two-tier: `mapctx store repair` reprojects `mapctx.db` from the independent journal for file-level corruption; total directory loss recovers only to the last git-tracked checkpoint, starting a new store incarnation.
      - [2026-08-15] Backup of the live store beyond checkpoint granularity is explicitly the user's responsibility; MapCtx does not add a backup/replication service in v1.
      - [2026-08-15] Under `plansAuthority: store`, the entire structured field block of `tasks/<ID>.md` is generated; only `description:` prose stays Git-authored. See T-049 tech plan.
      - [2026-08-16] Config succession is ordered and single-file: `mapcs.config.json` (root) pre-cutover, `mapctx.toml` after; import is the only bridge and deletes the old file. Root `sync.config.json` and `TASKS_SYNC_CONTEXT.md` removed as orphans before this task starts.
      - [2026-08-16] The inherited GitHub binding is unverified — no `read:project` scope, no `.mapcs/state.json`, all 68 `externalId: null`. Import must not present it as validated.
      - [2026-08-15] Canonical event journal lives outside `mapctx.db` (`events/<nodeId>/<sequence>.json`); SQLite holds index/projections only. Without this, repair cannot survive SQLite corruption.
      - [2026-08-16] TOML parsing uses `smol-toml` (new dep of `packages/store`); `mapctx.toml` resolution walks up from cwd (`findMapctxToml`, mirroring `core/workspace.ts`'s `findTasksRoot`) rather than resolving relative to cwd only, since worktrees change cwd but must resolve the same project store.
      - [2026-08-16] `packages/store` uses `node:sqlite` (`DatabaseSync`, Node ≥22.5, still flagged experimental upstream) per tech plan — no `better-sqlite3` native dependency. `WAL`, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=FULL` set on every connection.
      - [2026-08-16] `mapctx.toml`'s `[github]` table is the carried-over legacy binding (`owner`, `repo`, `projectId`, field IDs, `statusMap`, `verified: false`); `verified` is set only by a successful `mapctx sync status` authenticated read (checks `x-oauth-scopes` on `GET /user`), never by import.
      - [2026-08-16] `subIssueProgress` is derived at export time as `"<doneChildren>/<totalChildren>"` for any task with children (regardless of `type`), `null` otherwise — no prior spec pinned the exact format; this is the concrete choice.
      - [2026-08-16] The exporter does not reuse `@mapctx/core`'s `serializeTasksFile` for the generated snapshot: that function only conditionally emits most `REQUIRED_TASKS_MD_FIELDS` (matching the legacy hand-authored convention), while `board-tools.ts`'s validator requires all 16 present even when `null`. `packages/store/src/export.ts` has its own strict renderer that always emits them (`null`/`[]` fallback); `core`'s parser/serializer is untouched and still used for reading and for the pre-cutover path. Verified end-to-end: generated output passes `mapcs validate --json` (0 errors/warnings) on the real 69-task board.
      - [2026-08-16] `dependsOn`/`prerequisites`/`blocking` are rendered in lexical order (`dependency_projection`'s query order), not authored order — the only field class this applies to; `tags`/`domains`/`filesAffected`/`testsRequired`/etc. preserve insertion order. First cutover on the real board reorders 3 of 68 detail files' dependency lists for exactly this reason (byte-diff, not a data change).
      - [2026-08-16] `## Notes`/`## Work Domains` sections have a leading-blank-line quirk in the existing line-based parser (the blank separator after the heading becomes part of the captured section content). The store's importer normalizes it on read (`joinNotesSection`, `parseWorkDomains`); `core`'s parser/serializer themselves are unchanged to avoid widening blast radius on other consumers (`workspace-server.ts` et al.).
      - [2026-08-16] Duplicate `externalId` across tasks (violates `task_projection`'s unique index) is now a `planImport` validation error (`duplicate-external-id`), not a raw SQL constraint failure surfaced mid-commit — found via the round-trip property test.
      - [2026-08-16] `mapctx store init` recovers a lost `~/.mapctx/projects/<id>/` from the current `TASKS.md`/`tasks/*.md` (last git checkpoint) when `plansAuthority: store` and the store isn't materialized — new node + incarnation, same `projectId`. `mapctx import --commit` is not the re-entry point (it refuses whenever `mapctx.toml` already exists, which it does in this scenario); see Acceptance note.
      - [2026-08-16] Automatic `mapctx export` at wave/epic-end is not wired to a trigger — no wave-execution or epic-completion code exists yet in this repo (T-058 territory). The callable primitive (`export --reason wave-end|epic-end`) is ready for that caller.
