  - summary: Query compact task context under a declared token budget, and detect the semantic errors the structural validator accepts today.
  - description: |
      ## Product Context
      Two separate defects, one task. First: full-board Markdown is not low-token. `TASKS.md` is ~23 KB and the
      detail files together are ~115 KB — injecting the board wholesale costs tens of thousands of tokens, so
      "Markdown is cheap context" is only true with selective queries. Second: `mapcs validate` reports 0 errors on
      a board that contains a task finishing the day before it started. The validator checks shape, not sanity,
      which risks "deterministic" being mistaken for "correct."

      ## Expected Outcome
      An agent asks for one task and receives that task plus the context needed to act on it — ancestors, open
      dependencies, acceptance criteria, recent decisions — under a budget it declared, with anything omitted
      stated rather than silently dropped. Separately, the validator catches contradictions a human reader would
      catch.

      ## Acceptance

      ### Bounded context query
      - [x] `mapctx task show <id> --json` returns one task with its detail fields.
      - [x] `mapctx task context <id> --budget <n> --json` returns task, ancestor chain, unsatisfied dependencies,
            acceptance criteria, and the most recent `Decisions Taken` entries, bounded by `<n>` tokens.
      - [x] The tokenizer is named in the output (e.g. `"tokenizer": "<name>@<version>"`), not assumed. A character
            or word heuristic is acceptable for v1 **if** it is declared as such and its ratio is documented —
            what is not acceptable is an unlabeled number that reads like a real token count.
      - [x] Token counting is deterministic: same input, same reported count, asserted by test.
      - [x] Truncation is explicit. When content is dropped to fit the budget, the response names what was dropped
            and how much (e.g. `"truncated": [{"section": "decisions", "omitted": 4}]`). Silent truncation fails
            this criterion.
      - [x] Drop order is defined and documented, not incidental: the task's own acceptance and unsatisfied
            dependencies are the last things sacrificed, because they are what makes the context actionable.
      - [x] Provenance is reported per section — whether a field came from the store, from Git-authored prose, or
            was derived.
      - [x] Budget target is measured, not asserted: report the p50 and p90 context size across all non-done tasks
            on the real 71-task board. The 2k-token goal is a target to measure against and report honestly, not a
            number to make true by trimming until it fits.

      ### Semantic validation
      Extends the existing validator; does not replace its structural checks.
      - [x] Impossible dates are errors: `completed` before `start`, `due` before `start`, `completed` set on a
            non-`done` task, `done` task with no `completed`. **Fixture from the real board: T-044 has
            `start: 2026-02-25` and `completed: 2026-02-24`, and `mapcs validate` currently reports 0 errors.**
            That case must fail after this task.
      - [x] Stale/derived-field drift is detected: `subIssueProgress` disagreeing with children's actual completion,
            and a `updated` value that contradicts the task's own event history once the store is authoritative.
            **Fixture from the real board: 53 tasks share `updated: 2026-05-29`**, a bulk-write artifact that
            carries no information.
      - [x] Invalid graph links are errors: `parent`/`dependsOn` pointing at a nonexistent id, a task that is its
            own ancestor, and a dependency cycle (the existing cycle check may be reused).
      - [x] Each new check has a fixture derived from a real defect on this board where one exists, and a synthetic
            one where it does not. No check ships without a test that fails before the fix.
      - [x] Severity is deliberate per check and documented: contradictions are `error`, informational smells are
            `warning`. The real board must reach a stated, non-hand-waved status after this task — either it passes,
            or the remaining findings are listed and accepted explicitly.

      ### CLI wiring (carried over)
      - [x] `mapctx plan --json` is wired to `@mapctx/planner`'s `planExecution` (T-051 delivered the library; CLI
            wiring was deliberately deferred while `mapctx-cli.ts` was owned by T-060).

      ## Decisions Taken
      - [2026-08-17] "Below 2k tokens" is a measured, reported target, not an acceptance gate. The failure mode being
        avoided is trimming context until a number is satisfied and shipping an agent-hostile payload.
      - [2026-08-17] A heuristic tokenizer is acceptable for v1 provided it is labeled. The defect being fixed is an
        unlabeled count, not an imprecise one.
      - [2026-08-17] Implemented `mapctx-char-heuristic@1`: UTF-8 byte length divided by four, rounded up. Output
        includes method and ratio; counts are estimates, not provider/model token usage.
      - [2026-08-17] Real board measurement: 39 non-done tasks, p50 443 and p90 787 estimated tokens (min 262,
        max 1074). The 2k target is met by this heuristic, but remains a reported measurement rather than a gate.
      - [2026-08-17] Real-board validation now reports 2 errors (`T-044` completed-before-start and `E-008`
        subIssueProgress drift) and 2 warnings (53-task bulk `updated: 2026-05-29` smell plus one additional
        bulk timestamp finding). These are surfaced; no check is silenced to preserve green status.
      - [2026-08-17] CLI planner wiring now declares `@mapctx/planner: file:../planner` and resolves only the
        package name; build verification after this dependency edit is pending because the machine filesystem
        returned `ENOSPC`.
      - [2026-08-17] `mapctx plan` falls back to read-only `TASKS.md` when no store cutover exists, matching
        `mapcs plan`; store-authority projects still require materialized store. Runtime package-link verification
        remains open until root `npm install` is safe.
      - [2026-08-17] `mapctx task show/context` now use same pre-cutover fallback. Markdown task/detail fields carry
        `git` provenance; ancestors/dependencies remain `derived`; store-authority keeps `store` provenance.
        Smoke-tested T-061: show detail returned, context estimated 631 tokens at budget 800, acceptance 7,
        decisions 2, no truncation.
      - [2026-08-17] If mandatory task identity cannot fit tiny budget, context reports `budgetExceeded`,
        `minimumTokenCount`, and `budgetOverrun`; no silent over-budget result or extra identity truncation.
      - [2026-08-17] Semantic checks extend the current validator rather than replacing it; structural checks
        (required key order, detail-file existence, domain keys) stay exactly as they are.
      - [2026-08-17] Gated on T-060 for ordering, not logic: both need `mapctx-cli.ts`, and parallel edits to one
        hand-rolled CLI dispatch collide.
