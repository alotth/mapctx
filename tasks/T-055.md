# T-055

  - role: frontend
  - impact: high
  - estimatedEffort: 1w
  - prerequisites: [T-050, T-051, T-054]
  - blocking: [T-056]
  - filesAffected: [packages/vscode-extension/src/html/workspaceV2.js, packages/vscode-extension/src/html/workspaceV2.css, packages/sync-engine/src/mapctx-cli.ts, packages/forecast]
  - testsRequired: [view-model tests, empty-data honesty tests, coverage/confidence rendering tests, Gantt scenario tests]
  - summary: Replace the Gantt's hardcoded duration table with forecast and actuals, and make uncertainty visible instead of implied.
  - description: |
      ## Product Context
      The Gantt is the highest-value surface in MapCtx — the reason for the planning-intelligence direction is a
      delivery view that improves as real execution data accumulates. Today it is a picture of a lookup table.

      `workspaceV2.js` derives every bar from:

      ```js
      const WORKLOAD_DURATION_DAYS = { easy: 1, normal: 2, hard: 3, extreme: 5 };
      ```

      And on the real board, **0 of 37 non-done tasks have a `start` or a `due`**. So no bar on screen reflects a
      plan anyone made; every bar is a workload label multiplied by a constant. The chart looks like a schedule and
      is not one, which is worse than showing nothing — it is the same defect class as an unlabeled token count
      (T-050) or an `activeTime` that is really wall clock (T-054): a number that reads as measured and is not.

      T-054 now produces real `EstimateSnapshot`s with P50/P90, method, confidence, and coverage. T-060/T-061
      produce actuals and variance. This task connects them to the view.

      ## The state this must be honest in
      Design for the data that exists, not the data that will exist. On the real board today:

      - **planned dates: none.** Every `start`/`due` is null.
      - **actuals: none.** No cutover has run, so there are no receipts, no runs, no changed files.
      - **forecast: available, but weak.** No historical samples, so estimates fall back to a conservative prior at
        `confidence: low`, `method: expert-guess`, and duration coverage `substituted` (see T-064).

      A Gantt that only reads well with rich data fails on its first run, which is the run that decides whether
      anyone uses it again. Empty and low-confidence states are the primary design target here, not an edge case.

      ## Expected Outcome
      A delivery view where a reader can tell, at a glance and without reading docs, which bars are committed
      plans, which are forecasts, how uncertain those forecasts are, and what actually happened — and where
      "we don't know yet" is visibly different from "this is a one-day task."

      ## Acceptance

      ### Layers
      - [ ] Three layers render distinctly: **planned** (authored `start`/`due` — a human commitment), **forecast**
            (P50/P90 from `EstimateSnapshot`), and **actual** (spans derived from receipts). Distinguishable
            without relying on color alone.
      - [ ] The P50–P90 range is drawn as a range, not a point. A forecast rendered as a single hard-edged bar
            asserts precision the estimator does not claim.
      - [ ] A task with no authored dates shows no planned layer — it does **not** synthesize one. The absence is
            the information.
      - [ ] `WORKLOAD_DURATION_DAYS` is deleted. No duration anywhere is derived from a hardcoded workload table.
            If a task has neither dates nor a usable forecast, the view says so rather than inventing a width.

      ### Uncertainty and provenance
      - [ ] Each forecast bar exposes `confidence`, `method`, and `estimatorVersion` from its snapshot — visible on
            hover or in the task detail, not buried.
      - [ ] Duration coverage (`measured` | `substituted` | `none`, from T-054) is surfaced. A forecast built
            entirely on wall-clock substitution must be visually distinguishable from a measured one; today
            everything is `substituted`, so this is the common case, not the rare one.
      - [ ] An estimate derived from the conservative prior with no historical samples is labeled as such. It must
            not look like a calibrated forecast.

      ### Plan structure and execution truth
      - [ ] Dependency and wave structure from `@mapctx/planner` is visible — a reader can see why task B sits
            after task A, including when the cause is a resource-claim collision rather than a logical dependency.
      - [ ] Blocked tasks show their named reason from `blockedReasons` (`blocked by paused T-022`, `blocked by
            workflow gate architecture (pending)`), never silent absence. The planner already produces these.
      - [ ] Planned-versus-actual variance is shown where actuals exist, and the view degrades cleanly to
            forecast-only where they do not.
      - [ ] `ClaimViolation`s (T-061) surface against the wave they belong to.

      ### Data path
      - [ ] The view model is query-backed. A CLI command emits the complete Gantt dataset as JSON — planned,
            forecast, actual, wave structure, blockers, variance — and the view consumes that. No Markdown parsing
            and no duration computation in the browser; the view renders, it does not decide.
      - [ ] The dataset command works pre-cutover, like `plan`, `task show`, and `task context` already do.
      - [ ] The existing Kanban interaction that people actually use is preserved. This is a replacement of the
            duration model, not a rewrite of the workspace UI.

      ### Empty and degraded states
      - [ ] A board with zero forecasts and zero actuals renders a legible, honest view — tested explicitly
            against the current real board, which is exactly that board.
      - [ ] Tested: a task with planned dates but no forecast; a task with forecast but no planned dates (the
            common case today); a task with actuals exceeding its P90; a task blocked with a named reason.

      ## Decisions Taken
      - [2026-08-17] The frozen `workspace-server.ts` may gain exactly one data passthrough for the Gantt dataset
        and nothing else. The freeze (T-059, ADR 0003) exists to stop that surface growing into a cockpit, and it
        was preserved specifically because the planned-versus-actual Gantt needs a host — refusing the one thing it
        was kept alive for would be following the letter against the purpose. The boundary: the passthrough
        forwards CLI JSON and computes nothing. All computation stays in `@mapctx/forecast`, `@mapctx/planner`, and
        the CLI, consistent with "only the CLI opens the database."
      - [2026-08-17] Internal dogfood gates this work, not external adoption. ADR 0003 §Validation gates splits the
        two deliberately: the planning Gantt is core, not the operations cockpit that waits for external users.
      - [2026-08-17] Empty and low-confidence states are the primary design target, because they are the real
        board's current state and the first thing any new user sees.

      ## Open Decisions for Execution
      - Whether the Gantt is a new view alongside the existing roadmap timeline or replaces it. Replacing is
        cleaner if the current timeline has no behavior worth keeping once the fixed duration table is gone;
        decide after reading `renderTicks`/`roadmapGroupMode` and say which and why.

      ## Steps
      - [ ] Add the CLI command emitting the Gantt dataset; make it work pre-cutover.
      - [ ] Delete `WORKLOAD_DURATION_DAYS` and every path that reads it.
      - [ ] Render planned/forecast/actual layers with the P50–P90 range as a range.
      - [ ] Surface confidence, method, and coverage; distinguish prior-based from calibrated.
      - [ ] Show wave structure, named blockers, collisions, and variance.
      - [ ] Test the empty and low-confidence states against the real board.
