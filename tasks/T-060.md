# T-060

  - role: backend
  - impact: high
  - estimatedEffort: 4d
  - prerequisites: [T-049, T-052, T-058]
  - blocking: [T-054]
  - filesAffected: [packages/store/src/events.ts, packages/store/src/projections.ts, packages/store/src/schema.ts, packages/sync-engine/src/mapctx-cli.ts]
  - testsRequired: [dispatch-attempt persistence round-trip, receipt-write idempotency via evaluateRunReceipt, CLI receipt-ingest smoke test]
  - summary: Give dispatch/run/receipt a durable home in the store, closing the gap T-058 found before forecast needs to read it.
  - description: |
      ## Product Context
      T-058's walking skeleton proved store and protocol survive a real cross-worktree claim/release round trip, but
      found that `RunReceipt` has nowhere to land: `@mapctx/store`'s event types cover project/task/claim/checkpoint
      only, `evaluateRunReceipt` (T-052) is deliberately pure/stateless, and `mapctx-cli.ts` has no command path from
      "I have a receipt" to a store write. T-054 (forecast) needs "did the last attempt complete, what changed,
      what did it cost" to durably exist — without this task, forecast would either block or grow ad hoc receipt
      storage to route around the gap, which is exactly what T-058's writeup warned against.

      ## Expected Outcome
      A `RunReceipt` for a claimed task can be submitted once (CLI or programmatic call into `@mapctx/store`) and the
      result — outcome, changed files, usage, failure detail — is durably queryable per task and per dispatch
      afterward, across worktrees, the same way claim state already is.

      ## Acceptance
      - [x] `@mapctx/store`'s `EVENT_TYPES` gains dispatch/run event kinds (`dispatch.attempted`,
            `run.receipt-recorded`) following the existing granularity rule: one event per coherent state change, not
            per field.
      - [x] A `dispatch_projection`/`run_receipt_projection` (or equivalent) materializes attempt history per
            `dispatchId`, queryable by task, so "did the last attempt complete" is a store read, not something a
            caller has to reconstruct.
      - [x] Store-side write path calls `evaluateRunReceipt` (T-052, `attempt-lifecycle.ts`) before persisting — a
            stale or duplicate receipt is rejected at the store boundary with the same `stale-attempt`/
            `duplicate-receipt`/`unknown-attempt`/`dispatch-mismatch` reasons T-052 already defines, not a second
            idempotency implementation.
      - [x] `mapctx-cli.ts` gains a command (`mapctx dispatch receipt <dispatchId> --receipt <path> --json`, or JSON stdin), reading a
            `RunReceipt` payload that performs the write, alongside the existing `claim`/`renew`/`release` trio.
      - [x] Receipt write updates `Task.executionState`/`planningState` per the existing `EXECUTION_TRANSITIONS` state
            machine (`packages/protocol/src/state-machines.ts`) — a `completed` outcome cannot silently skip an
            illegal transition.
      - [x] Cross-worktree test: submit a receipt from worktree A, confirm it is visible identically (attempt history,
            outcome, changed files) from worktree B resolving the same store — same pattern T-058 already proved for
            claim/release.
      - [x] `usageEvents`/`failure` on the receipt persist losslessly (no derived-field loss) so T-054 can read them
            without re-deriving from a payload it doesn't have.

      ## Decisions Taken
      - [2026-08-16] This is a store-layer gap, not a T-052 gap — `evaluateRunReceipt` stays pure/stateless by design
        (T-052's own acceptance); T-060 is the caller that gives it a durable home. No change to `packages/protocol`
        expected; if one turns out to be load-bearing, flag it rather than editing T-052's contract silently.
      - [2026-08-16] Scoped narrower than T-053 (Traycer adapter automation): T-060 makes the store able to accept a
        receipt from any source; it does not build the automation that produces one from a live Traycer execution.
      - [2026-08-17] Added `dispatch.attempted` and `run.receipt-recorded` as the two coherent state-change events.
        Dispatch projections use `(dispatchId, attempt)` as identity so retries retain history. Receipt writes call
        `evaluateRunReceipt` before journaling, then enforce execution/dispatch/planning transitions in projection
        application. Full receipt JSON is retained alongside indexed usage rows to keep `usageEvents`, `evidence`, and
        `failure` lossless. CLI accepts `--receipt <path>` or stdin.
      - [2026-08-17] Completed receipt moves execution to `completed` and planning to `review`; it never self-approves
        work into `done`. Failed receipts move `in-progress`/`blocked` planning back to `ready` (or preserve existing
        `ready`/`backlog`), blocked receipts move planning to `blocked`, and cancelled receipts leave planning unchanged.
      - [2026-08-17] Acceptance #6 completed: disposable detached Git worktrees A/B resolved identical `mapctx.toml`
        and shared `MAPCTX_HOME`; A submitted receipt through CLI, B read attempt/receipt through CLI with identical
        outcome and `changedFiles`. Worktrees and temporary store were removed afterward.
      - [2026-08-17] Migration 001 was edited in place because no project has performed cutover and no real store with
        its old checksum exists. After first cutover, all schema changes must use a new numbered migration: the
        checksum guard in `schema_migrations` intentionally hard-fails on an edited applied migration. Existing
        checksum-divergence test in `migration.test.ts` confirms this guard.

      ## Open Decisions for Execution
      - Exact event-type names and projection shape are implementation-time calls, not fixed here — follow the
        existing `events.ts`/`projections.ts` conventions from T-049 rather than inventing new ones.

      - [x] Wire receipt outcome into `EXECUTION_TRANSITIONS`.
