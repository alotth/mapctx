  - description: |
      ## Product Context
      Two resolution models coexist and disagree. `mapctx.toml` is resolved by walking parent directories up from
      cwd (the `findTasksRoot` pattern in `packages/core/src/workspace.ts`, chosen in T-049 precisely because
      worktrees change cwd). The board itself is resolved as `cwd/TASKS.md`, literally. So the newer, store-side
      half of the CLI works from anywhere in the repo and the older, board-side half only works from the root.

      Observed on the real repo:

      ```
      $ cd packages/store && mapctx plan --json
      Error: ENOENT: no such file or directory, open '.../packages/store/TASKS.md'

      $ cd packages/store && mapcs plan --json
      Error: Config not found: .../packages/store/mapcs.config.json. No tasks file found at .../packages/store/TASKS.md.
      ```

      This is pre-existing, not a regression from T-050 — `mapcs` behaves identically and always has. It matters more
      now because agents and worktrees run from varied working directories, and because T-050 made the read-only
      commands (`task show`, `task context`, `plan`) the primary interface for agents. A command an agent cannot
      call from where it happens to be standing is a command it will work around.

      ## Expected Outcome
      Any read-only board command resolves the same project from any directory inside the repository, matching the
      resolution rule already used for `mapctx.toml`, and both CLIs agree on where the board is.

      ## Acceptance
      - [x] Board resolution walks parent directories from cwd until it finds `TASKS.md` (or the configured
            `tasksFile`), reusing `findTasksRoot` from `@mapctx/core/workspace` rather than adding a second
            walk-up implementation.
      - [x] `mapctx plan`, `mapctx task show`, `mapctx task context`, and `mapctx validate` all work from a nested
            subdirectory (e.g. `packages/store/`), asserted by test, not by manual check.
      - [x] `mapcs validate` and `mapcs plan` get the same treatment, so the two CLIs do not disagree about where
            the board is during the deprecation window.
      - [x] An explicit `--tasks-file <path>` continues to win over discovery, unchanged.
      - [x] Resolution stops at the repository root and does not escape it — a `TASKS.md` in a parent directory
            outside the repo is never silently adopted.
      - [x] The resolved board path is reported in `--json` output so a caller can tell which board answered.
      - [x] Test covers a git worktree, not only a subdirectory, since that is the case T-049's resolution rule
            was designed for.

      ## Decisions Taken
      - [2026-08-17] Found during T-050 verification; deliberately not fixed there because it is pre-existing in
        `mapcs` and outside that task's scope. Filed rather than folded in.
      - [2026-08-17] Reuse `findTasksRoot`; a second walk-up implementation is exactly the duplication that made
        the two resolution models diverge in the first place.
      - [2026-08-26] "Repository root" = nearest `.git` (directory or worktree file), checked after the tasks-file
        candidate at each level so a `TASKS.md`/`tasksFile` sitting exactly at the git root still resolves;
        `mapctx.toml` discovery (`findMapctxToml` in `@mapctx/store`) already had its own independent walk-up and
        was left untouched — it is store-mode detection, not board-file resolution, and out of scope here.
      - [2026-08-26] `findTasksRoot` took an optional `tasksFile` param so `mapcs.config.json` discovery and
        `TASKS.md` discovery reuse the same walk-up with different filenames, instead of adding a second resolver.
      - [2026-08-26] `mapctx validate --json` was double-emitting JSON (validation report + store-regime object
        concatenated). Fixed by extracting `getValidationReport` (report-only, no printing) and having the CLI
        emit one merged object `{ ...validation, store: storeResult }`.
      - [2026-08-26] Found and fixed a `ReferenceError` in `mapctxPlanCommand`'s pre-cutover branch: it referenced
        an undefined `tasksFilePath` when building `--json` output. Pre-existing bug in this worktree's
        uncommitted T-055/gantt-adjacent edit to that function, not something I introduced — fixed in place since
        it broke the exact acceptance criterion (resolved path in plan JSON) and had a failing test to prove it.
      - [2026-08-26] Independent gate found a second resolver bug: config discovery found the root
        `mapcs.config.json`, then `loadConfig()` reopened `cwd/mapcs.config.json`. The discovered absolute path is
        now passed through, with a nested-cwd test whose configured board is `boards/WORK.md` rather than
        `TASKS.md`.
      - [2026-08-26] Fresh review found store-authority reads had become dependent on Markdown solely to populate
        provenance. Store `plan/show/context` now derive the checkpoint path and detail root from `mapctx.toml`;
        they remain store-backed and work when `TASKS.md`/`mapcs.config.json` are absent.
      - [2026-08-26] A board-resolution failure under `mapctx validate --json` emits one
        `board-resolution-failed` JSON document before returning failure, instead of producing empty stdout.
