# T-063

  - role: backend
  - impact: high
  - estimatedEffort: 2d
  - prerequisites: [T-050, T-051]
  - blocking: []
  - filesAffected: [packages/planner/src/index.ts, packages/sync-engine/src/mapctx-cli.ts, packages/protocol/docs]
  - testsRequired: [edge direction test per kind, silent-drop regression test, real-board plan completeness test, CLI/library parity test]
  - summary: Fix inverted depends-on edge handling and make unschedulable tasks report a reason instead of vanishing.
  - description: |
      ## Product Context
      Found by running `mapctx plan` on this repository's own board, immediately after T-050 wired the CLI to the
      T-051 planner. The plan silently omitted `T-053`, `T-054`, `T-055`, `T-056`, and `T-057` — five real, ready
      tasks — and returned `recommended: []`. The omission had no entry in `blockedReasons`. The plan looked
      plausible, which is what made it dangerous: it was about to be used to decide what to dispatch next.

      Reproduction, calling the library directly with and without the CLI's edge list:

      ```
      without dependencyEdges: [T-016,T-054] [T-017,T-055] [T-021,T-062] [T-031,T-053] [T-034] [T-056] [T-057]
      with    dependencyEdges: [T-016,T-062] [T-017] [T-021] [T-031] [T-034]
      ```

      ## Root cause
      Two defects compound, and a third hides them.

      **1. `depends-on` is read backwards.** `packages/planner/src/index.ts` treats both edge kinds identically:

      ```ts
      if (edge.kind === "blocks" || edge.kind === "depends-on") dependencies.get(edge.toTaskId)?.add(edge.fromTaskId);
      ```

      That is correct for `blocks` (`from` blocks `to`, so `to` waits on `from`) and inverted for `depends-on`
      (`from` depends on `to`, so `from` waits on `to`). The two kinds are not the same relation with the same
      direction; collapsing them into one branch is the bug.

      **2. The CLI double-specifies dependencies.** `mapctxPlanCommand` passes `dependsOn` on every task *and*
      re-encodes the identical information as `dependencyEdges`. Even once direction is fixed, sending the same
      relation twice invites the two representations to disagree.

      **3. Unschedulable tasks disappear silently.** The tasks were dropped from the wave output with nothing in
      `blockedReasons`. T-051's stated guarantee is that exclusions are named — a task that cannot be scheduled
      must say why. Silence is what let a direction bug look like a valid plan.

      ## Expected Outcome
      Every non-terminal task appears in the plan either as scheduled work or as an explicitly blocked task with a
      named reason. Edge direction matches the protocol's semantics per kind, and the CLI and the library produce
      identical plans from the same board.

      ## Acceptance
      - [x] `depends-on` and `blocks` are handled as distinct directions: for `{from, to, kind: "depends-on"}`,
            `from` waits on `to`; for `{from, to, kind: "blocks"}`, `to` waits on `from`. Test asserts both
            directions independently, not one test covering "edges work."
      - [x] The direction semantics are documented where `DependencyEdge` is defined so the next consumer does not
            have to infer them from planner internals.
      - [x] Invariant test: every task that is neither terminal nor a container appears in the output, either in a
            wave or in `blockedReasons`. Run against the real 72-task board, not only fixtures — the real board is
            what exposed this.
      - [x] Regression test pinning this exact case: a board where a ready task depends on a completed task must
            schedule that task, and must not drop it.
      - [x] CLI and library agree: planning the same board through `mapctx plan --json` and through a direct
            `planExecution` call produces identical wave assignment, asserted by test.
      - [x] The CLI stops sending the same dependency relation twice — pick `dependsOn` or `dependencyEdges` as the
            single representation for board-sourced plans and document which.
      - [x] `mapctx plan` on this repository lists `T-053`, `T-054`, `T-055`, `T-056`, `T-057` again, and
            `recommended` is non-empty.

      ## Decisions Taken
      - [2026-08-17] Found by dogfooding `mapctx plan` on this board before dispatching T-053/T-054. The plan was
        used as the input to a real dispatch decision and was wrong — filed as high impact for that reason, not
        for the size of the fix.
      - [2026-08-17] The silent drop is treated as a separate defect from the direction bug, and the more serious
        of the two: the direction bug produced a wrong answer, the silence made it look right.
      - [2026-08-17] Direction semantics confirmed as diagnosed, not inverted: `blocks` was already correct
        (`to` waits on `from`); only `depends-on` was backwards. Fixed by splitting the single `if` branch into
        two, one per kind, in `packages/planner/src/index.ts`.
      - [2026-08-17] Closed the silent-drop hole for two more cases beyond the reported one, so the completeness
        invariant holds unconditionally rather than only for the specific bug that exposed it: (1) tasks left
        over in `cycleTaskIds` after wave-building now get a `kind: "cycle"` `blockedReasons` entry; (2)
        non-terminal, non-container tasks excluded purely by their own status (paused/review/in-progress/blocked)
        now get a `kind: "status"` `blockedReasons` entry instead of only appearing in `excludedTaskIds`.
      - [2026-08-17] Chose `dependencyEdges` as the single representation the CLI sends to the planner for
        board-sourced plans (both the TASKS.md fallback and the store-backed path); `dependsOn` is no longer
        passed alongside it. Documented in `packages/protocol/docs/dependency-edges.md`.

      ## Steps
      - [x] Split `depends-on` and `blocks` handling in the planner.
      - [x] Add the completeness invariant (scheduled or explicitly blocked) with a real-board assertion.
      - [x] Collapse the CLI's double dependency specification to one representation.
      - [x] Document edge direction next to the `DependencyEdge` definition.
