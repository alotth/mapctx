# T-064

  - role: backend
  - impact: medium
  - estimatedEffort: 3d
  - prerequisites: [T-060, T-054]
  - blocking: []
  - filesAffected: [packages/store/src/events.ts, packages/store/src/dispatch.ts, packages/store/src/schema.ts, packages/forecast/src/duration.ts]
  - testsRequired: [run-event persistence round-trip, active-time gap subtraction from stored events, coverage downgrade test]
  - summary: Persist RunEvent timestamps so activeTime can be measured instead of falling back to wall clock.
  - description: |
      ## Product Context
      ADR 0003 §Time model separates four measures and states that forecast P50/P90 uses `activeTime`, precisely so
      a session left open overnight does not turn 40 minutes of work into 14 hours of "execution." T-054 implemented
      `activeTimeMs(timestamps, idleThresholdMs)` correctly — it sums only inter-event gaps below the threshold.

      But nothing feeds it real timestamps. `RunReceipt` carries only `startedAt` and `endedAt`, and the store
      persists `dispatch.attempted` and `run.receipt-recorded` — never the individual `RunEvent`s. So
      `durationFromReceipt` returns `activeTimeMs: sessionWallClockMs`, which is honest in its code comment and
      invisible to any consumer reading the field.

      The result: forecast today inherits idle time while reporting a field named `activeTime`. That is the exact
      failure the ADR's time model exists to prevent, and it is the same class of defect T-050 fixed for token
      counts — the problem is the unlabeled number, not the imprecision.

      The protocol already has what is needed. `runEventSchema` (`packages/protocol/src/envelopes.ts`) carries
      `timestamp`, `sequence`, and a `type` enum including `heartbeat` and `progress`. The gap is storage only.

      ## Expected Outcome
      `activeTime` is measured from real intra-run timestamps when a harness emits them, falls back to wall clock
      when it does not, and always states which of the two happened so a forecast built on partial coverage is not
      mistaken for a measured one.

      ## Acceptance
      - [ ] `@mapctx/store` persists `RunEvent`s against their `(dispatchId, attempt)`, following the existing
            append-only event and projection conventions. Ordering by `sequence` is preserved.
      - [ ] `durationFromReceipt` (or its replacement) reads stored `RunEvent` timestamps when present and computes
            `activeTimeMs` by real gap subtraction, using the existing `activeTimeMs` helper unchanged.
      - [ ] Duration measures carry a coverage marker in the same spirit as `UsageEvent.source`/`coverage` — a
            consumer can tell whether `activeTime` was measured from events or substituted from wall clock. A
            substituted value is never presented as measured.
      - [ ] `EstimateSnapshot` records the duration coverage it was built from, so a forecast derived entirely from
            wall-clock substitution is identifiable after the fact rather than indistinguishable from a measured one.
      - [ ] Test: a dispatch with events spanning a long idle gap yields `activeTime` materially lower than
            `sessionWallClock`, and the coverage marker says `measured`.
      - [ ] Test: a dispatch with no stored events yields `activeTime == sessionWallClock` and a coverage marker
            saying substituted — asserted explicitly, not left implicit.

      ## Decisions Taken
      - [2026-08-17] Found during T-054 verification. The T-054 agent flagged the limitation honestly in a code
        comment rather than hiding it; filed as its own task rather than expanding T-054's scope, following the
        same pattern as T-058 → T-060.
      - [2026-08-17] Labeling is required immediately (handled in T-054); measuring is this task. A wrong number
        that announces itself is a known limitation, a wrong number that looks right is a trap.

      ## Open Decisions for Execution
      - Whether to persist every `RunEvent` or only those carrying timestamps useful for gap analysis
        (`heartbeat`, `progress`, `started`, terminal). Volume matters here — a chatty executor could write many
        events per run. Decide at implementation and document the rule.

      ## Steps
      - [ ] Add run-event persistence to the store's event types and projections.
      - [ ] Wire stored timestamps into duration measurement.
      - [ ] Add the coverage marker to duration measures and `EstimateSnapshot`.
      - [ ] Test both the measured and substituted paths explicitly.
