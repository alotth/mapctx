# T-065

  - blocking: [T-057]
  - filesAffected: [packages/forecast/src/estimate.ts, packages/forecast/src/types.ts, packages/vscode-extension/src/html/workspaceV2.js, docs/adr]

  - summary: Make the duration prior workload-aware and unit-honest, so estimates can shrink toward agent-speed reality instead of staying anchored to human working days.
  - description: |
      ## Product Context
      Estimation on this board is anchored to human development pace, and agent-assisted work is roughly an order
      of magnitude faster. The anchor shows up as authored day/week estimates and as a hidden hourly constant in
      the forecast prior.

      Measured on this repository's own history — the twelve tasks closed on 2026-08-16 and 2026-08-17:

      | | |
      |---|---|
      | Authored `estimatedEffort` | 3d + 1w + 1w + 1w + 4d + 1w + 1w + 2.5w + 3d + 4d + 4d + 2d = **57.5 days** |
      | Actual elapsed | **~2 days** of wall clock, far less in active time |
      | Ratio | **~28x** |

      This is not "days should have been hours." It is "weeks of estimate took hours." Every one of those numbers
      was written by an agent or by a coordinator reasoning about human delivery pace, because that is what the
      training data and the surrounding conventions describe.

      ## The anchor is in two places

      **1. Authored `estimatedEffort` is free text (`"1w"`, `"3d"`) and feeds nothing.** The forecast does not read
      it. It is a human intuition recorded in a human unit, and it is wrong by more than an order of magnitude.

      **2. The forecast prior is a flat, workload-blind constant.**

      ```ts
      export const DEFAULT_PRIOR: ForecastPrior = {
        durationP50Ms: 8 * HOUR_MS,
        durationP90Ms: 16 * HOUR_MS,
        ...
      }
      ```

      Eight hours is one human working day. There is no reference to `workload` anywhere in `@mapctx/forecast`, so
      an `Easy` task and an `Extreme` task receive an identical forecast. That is the same defect class T-055 is
      deleting from the Gantt — a hidden constant standing in for a measurement — and in one respect it is worse,
      because the table it replaces at least varied by difficulty.

      Storage is not the problem: every duration is already milliseconds (`durationP50Ms`, `activeTimeMs`,
      `sessionWallClockMs`, `idleThresholdMs`). No schema change is needed. This is about priors and presentation.

      ## Expected Outcome
      A first estimate that reflects agent-speed reality rather than a human working day, varies with declared
      difficulty, and is displayed in whatever unit the magnitude actually calls for. As actuals accumulate the
      prior stops mattering, which is the real fix — this task makes the starting point defensible and the path
      to calibration visible.

      ## Acceptance

      ### Prior
      - [ ] The duration prior varies by `workload` (`Easy | Normal | Hard | Extreme`) instead of being one flat
            constant. A task's declared difficulty is the only signal available before any history exists;
            ignoring it discards the one input there is.
      - [ ] Prior values are derived from this repository's measured history where it exists, not from human
            working-day intuition, and the derivation is written down. A guess is acceptable; an undocumented
            guess presented as a baseline is not.
      - [ ] The prior is data, not a literal buried in code — replaceable without editing `estimate.ts`, so
            recalibration does not require a release.
      - [ ] `assumptions` states which prior was used and that it is a prior, distinguishable from a
            history-derived estimate. Extends what T-054 already does for coverage.

      ### Calibration path
      - [ ] Once a task has real actuals, `method` moves `expert-guess → historical-baseline`, and the transition
            is asserted by test rather than assumed. The schema already carries the vocabulary; nothing exercises
            the transition today.
      - [ ] Estimates are grouped by `workload` when computing historical baselines, so "how long does an Extreme
            task take here" becomes answerable rather than averaging across all difficulties.
      - [ ] A report compares authored `estimatedEffort` against measured actuals, so the anchor drift is
            observable instead of anecdotal. This board's ~28x gap is the first fixture.

      ### Units and display
      - [ ] Duration display picks its unit from magnitude — minutes, hours, or days — rather than a fixed unit.
            A 20-minute task rendered as "0.04d" is unreadable and a 3-day task rendered as "4320m" is worse.
      - [ ] The Gantt handles mixed magnitudes on one axis. A chart spanning a 20-minute task and a 3-day task
            cannot use one linear day scale and stay legible; decide the approach (non-linear axis, grouping,
            zoom, or per-wave scaling) and document why. This is the hard part of this task, not the prior.
      - [ ] `estimatedEffort` gets an explicit disposition: parsed into milliseconds and treated as a declared
            prior, or deprecated in favour of `EstimateSnapshot`. Today it is free text that nothing reads, which
            is the worst of both.

      ## Decisions Taken
      - [2026-08-17] Storage stays in milliseconds; the unit question is presentation and priors, not schema.
        No protocol change expected.
      - [2026-08-17] The flat 8h/16h prior is treated as the same defect class as the Gantt's
        `WORKLOAD_DURATION_DAYS` table — a hidden human-anchored constant rendered as a forecast — and filed
        alongside it rather than left as a footnote in T-054.
      - [2026-08-17] Expect the anchor to correct itself as actuals accumulate; this task exists so the starting
        point is defensible and the correction is measurable, not to guess the right number once.

      ## Open Decisions for Execution
      - Whether prior values come from a vendored data file (like the price table) or from computed history once
        enough exists. The price table precedent argues for vendored-and-versioned as the v1 shape.

      ## Steps
      - [ ] Make the prior workload-aware and move it out of code into data.
      - [ ] Derive initial values from this repository's measured history and document the derivation.
      - [ ] Group historical baselines by workload and test the `expert-guess → historical-baseline` transition.
      - [ ] Add magnitude-based unit formatting.
      - [ ] Decide and document the mixed-magnitude Gantt axis approach.
      - [ ] Give `estimatedEffort` an explicit disposition.
