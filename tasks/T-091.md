  - summary: Promote cancelled from protocol-only state to full board vocabulary: movable via task move, exportable to TASKS.md, reopenable like archived, visible/filterable in workspace UI, documented. Distinguishes 'aborted after starting' from archived 'will not proceed'.
  - description: |
      ## Problem
      `cancelled` is a first-class PlanningState in the protocol (terminal, reachable from
      backlog/ready/blocked/in-progress/paused) but has no board vocabulary: `task move --status cancelled`
      is refused as state-not-exportable, TASKS.md cannot represent it, and the workspace UI has no
      ordering/filter treatment for it. Semantics: cancelled = aborted after starting (vs archived = will
      not proceed).

      ## Decisions taken
      - Board vocabulary grows: STATUS_TO_PLANNING gains cancelled; DEFAULT_ALLOWED_STATUSES + DEFAULT_STATUS_MAP gain it (validateStatusConfig stays consistent).
      - review -> cancelled becomes a legal transition (mirrors in-progress -> cancelled; review -> archived already exists).
      - `task reopen --status review` also accepts cancelled, matching done/archived recoverability.
      - UI: cancelled joins DEFAULT_STATUS_ORDER and is hidden from the default filter view like archived (available via its chip).
      - Terminal for dispatch/claims is already enforced (context/dispatch/claims checks); gantt TERMINAL_STATUSES already includes cancelled.
      - GitHub statusMap in mapctx.toml intentionally NOT extended: remote option creation is a separate concern; push-store skips unmapped statuses gracefully.

      ## Follow-up (same-day)
      Filter chips were data-derived, so the Cancelled chip vanished once no task had that
      status (the verification stub was archived). workspaceFilterStatuses() now pins the full
      DEFAULT_STATUS_ORDER vocabulary in the filter row (data-only statuses append after),
      keeping Cancelled/Archived reachable with zero matching tasks. Verified live on 4173.
